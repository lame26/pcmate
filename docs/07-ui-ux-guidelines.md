# PC 견적 빌드업 웹앱 UI/UX 기준 문서

이 문서는 PC 견적 빌드업 웹앱의 상업용 MVP 화면 설계와 구현을 위한 판단 기준이다. 특정 화면 레이아웃, 색상, 섹션 순서, 컴포넌트 배치를 확정하지 않고, 앞으로 디자이너·개발자·AI 코딩 에이전트가 일관된 품질로 의사결정할 수 있는 기준을 제공한다.

## 0. 프로젝트 이해 요약

### 확인된 프로젝트 성격

| 항목 | 판단 |
| --- | --- |
| 서비스 유형 | B2C 웹앱 |
| 제품 중심 | 랜딩 중심보다 앱 중심 |
| 핵심 UX | 단계형 입력, 조건 판독, 후보 비교, 최종 견적 출력 |
| 주요 데이터 | PC 사양, 게임/작업 조건, 부품 후보, 가격/혜택가, 신뢰도, 경고 |
| MVP 저장 방식 | 로그인/DB 없이 localStorage 우선 |
| 기술 스택 | Next.js App Router, TypeScript, Tailwind CSS, shadcn/ui, Zustand |
| 서비스 톤 | 판매 유도형이 아닌 보수적이고 신뢰성 있는 상담형 |

### 확인된 핵심 사용자 흐름

1. 새 견적 시작 또는 이전 견적 복구
2. 보유 카드 선택
3. 현재 PC 사양 입력 또는 PowerShell 결과 붙여넣기
4. 게임, 작업, 모니터, VR, 예산, 선호도 입력
5. 사양 판독 결과 확인
6. 가격 데이터 보강
7. CPU부터 케이스까지 단계별 부품 후보 선택
8. 최종 견적 확인
9. 텍스트 복사 또는 이미지 저장

### UI/UX상 중요한 전제

- 사용자는 PC 부품 지식이 부족할 수 있지만, 가격과 성능 판단에는 민감하다.
- 추천 결과는 단정이 아니라 근거와 신뢰도, 주의사항을 함께 제공해야 한다.
- 가격 데이터와 크롤링 결과는 불완전할 수 있으므로 실패·부족 상태가 정상 흐름 안에 포함되어야 한다.
- MVP는 데스크톱 중심으로 설계하되, 모바일에서도 주요 입력과 최종 견적 확인이 가능해야 한다.

## 1. 문서 목적

### 왜 필요한가

이 서비스는 단순 랜딩페이지가 아니라 긴 입력 흐름, 계산 결과, 추천 후보, 가격 신뢰도, 경고 상태가 결합된 의사결정 도구다. 화면마다 설계자가 달라지면 사용자는 같은 서비스 안에서도 정보의 중요도, 버튼 의미, 경고 수준, 가격 신뢰도를 다르게 해석할 수 있다.

이 문서는 MVP 단계에서 과설계를 막으면서도 상업용 서비스처럼 보이는 기본 품질을 유지하기 위한 공통 기준이다.

### 누가 언제 참고하는가

| 작업자 | 참고 시점 |
| --- | --- |
| 제품 기획자 | 기능 범위와 화면 목적을 정리할 때 |
| UI/UX 디자이너 | 화면 구조, 정보 우선순위, 상태 설계를 검토할 때 |
| 프론트엔드 개발자 | 컴포넌트, 상태, 반응형, 접근성 구현 기준을 정할 때 |
| AI 코딩 에이전트 | 화면을 구현하기 전 요구사항을 해석하고 품질을 점검할 때 |

### 이 문서가 확정하는 것

- UI/UX 의사결정 원칙
- 화면 설계 시 검토해야 할 기준
- 컴포넌트와 상태 표현의 역할
- MVP에서 반드시 지켜야 할 사용성·신뢰성·접근성 기준
- 확장 시 UI가 무너지지 않도록 하는 판단 기준

### 이 문서가 확정하지 않는 것

- 특정 랜딩페이지 구조
- 특정 대시보드 구조
- 특정 컬러 팔레트
- 특정 radius, spacing, breakpoint 값
- 특정 섹션 수나 배치
- 기능 요구사항 추가
- 실제 화면 구현

## 2. 프로젝트 UI/UX 목표

### 사용자에게 줘야 할 인상

이 서비스는 사용자가 PC 견적을 “구매 압박”이 아니라 “근거 있는 상담”으로 받아들이게 해야 한다. 사용자는 추천 결과를 보며 다음을 느껴야 한다.

- 내 사용 조건이 제대로 반영되었다.
- 가격과 혜택가는 조건부 정보라는 점이 명확하다.
- 추천 이유와 경고가 투명하다.
- 모르는 용어가 있어도 다음 행동을 결정할 수 있다.
- 최종 견적이 복사·저장 가능한 실용적 결과물이다.

### MVP 단계에서 반드시 확보할 품질

- 주요 플로우가 끊기지 않는다.
- 입력값이 저장되고 새로고침 후 복구된다.
- 가격 데이터가 부족하거나 실패해도 사용자가 다음 행동을 이해할 수 있다.
- 추천 후보에는 점수뿐 아니라 이유와 주의사항이 붙는다.
- 핵심 CTA와 보조 행동이 명확히 구분된다.
- 모바일에서도 주요 입력과 최종 확인이 가능하다.

### 상업용 서비스처럼 보이기 위한 최소 기준

- 화면 목적이 한눈에 드러난다.
- 정보 그룹과 액션의 위계가 일관된다.
- 가격, 혜택, 경고, 신뢰도 표기가 화면마다 동일한 의미를 가진다.
- 기본 상태, 로딩, 빈 데이터, 오류, 성공 상태가 빠지지 않는다.
- 폼 라벨, 오류 문구, 도움말이 사용자를 탓하지 않는다.
- 장식보다 판단에 필요한 정보가 우선한다.

### 피해야 할 인상

- 광고성, 과장 판매, 핫딜 선동처럼 보이는 인상
- “무조건 정답”을 제시하는 인상
- 부품 지식이 있는 사람만 이해할 수 있는 인상
- 가격 조건과 신뢰도를 숨기는 인상
- 입력이 길고 복잡한데 현재 위치를 알 수 없는 인상
- 카드, 배지, 차트, 아이콘을 과도하게 사용해 산만한 인상

## 3. 사용자와 사용 맥락

### 예상 사용자 유형

| 사용자 유형 | 주요 니즈 | UI/UX 고려 |
| --- | --- | --- |
| PC 초보 구매자 | 어떤 사양이 적정한지 알고 싶음 | 용어 설명, 추천 이유, 과투자 경고 |
| 업그레이드 고민 사용자 | 일부 교체와 전체 교체를 비교하고 싶음 | 재사용 부품 입력, 호환성 경고 |
| 게임 중심 사용자 | 게임과 모니터 기준 적정 GPU/CPU를 알고 싶음 | 게임별 목표 옵션, 고사양 기준 우선 |
| 작업/멀티태스킹 사용자 | RAM, CPU, GPU 필요도를 알고 싶음 | 동시 실행 환경 입력, 이유 기반 결과 |
| 가격 민감 사용자 | 카드 혜택가와 최종 결제 예상액을 알고 싶음 | 조건부 혜택, 배송비, 신뢰도 표시 |

### 사용 상황

- PC를 새로 맞추기 전 대략적인 견적 방향을 잡는 상황
- 기존 PC를 유지할지 교체할지 판단하는 상황
- 게임이나 작업 환경 변화로 요구 사양을 다시 계산하는 상황
- 다나와 가격, 카드 혜택, 쇼핑몰 조건을 비교하는 상황
- 최종 견적을 커뮤니티나 지인에게 공유하기 전 정리하는 상황

### 사용자의 주요 목표

- 내 사용 조건에 맞는 적정 사양을 파악한다.
- 부품별 후보를 비교하고 선택한다.
- 카드 혜택가 기준 최종 금액을 확인한다.
- 가격 데이터가 얼마나 믿을 만한지 판단한다.
- 복사하거나 이미지로 저장할 수 있는 견적 결과를 얻는다.

### 사용자가 불편해할 수 있는 지점

- 입력해야 할 항목이 많다고 느끼는 지점
- PC 부품명, 티어, 칩셋, VRAM 같은 용어가 어려운 지점
- 가격 조건이 복잡하거나 실제 결제 금액과 다를 수 있는 지점
- 추천 결과가 왜 나왔는지 이해하지 못하는 지점
- 모바일에서 표나 후보 비교가 읽기 어려운 지점

### 신뢰를 얻어야 하는 지점

- 가격과 혜택가의 적용 조건
- 크롤링 또는 붙여넣기 가격 데이터의 갱신 시각
- 게임 요구사양 데이터의 출처와 신뢰도
- 호환성 경고의 심각도
- 추천 후보의 이유와 한계

## 4. 정보 구조 원칙

### 정보 우선순위 기준

화면의 정보는 사용자가 다음 행동을 결정하는 데 필요한 순서로 배치한다.

1. 현재 화면에서 해야 할 일
2. 입력 또는 확인해야 할 핵심 정보
3. 결과 판단에 직접 영향을 주는 경고와 신뢰도
4. 보조 설명과 상세 근거
5. 고급 사용자용 세부 정보

### 핵심 정보와 보조 정보 구분

핵심 정보는 화면의 주요 결정을 바꾸는 정보다. 예를 들어 부품 후보 화면에서는 상품명, 실결제 예상가, 추천 이유, 호환성 경고가 핵심이다. 칩셋 상세, 유통사 세부 근거, 원문 가격 데이터는 보조 정보로 접거나 상세 영역에 둘 수 있다.

### 처음 보는 사용자를 위한 기준

- 화면 제목은 기능명이 아니라 사용자의 현재 과업을 설명해야 한다.
- 전문 용어는 결과 해석에 필요한 경우에만 노출하고, 짧은 도움말을 제공한다.
- 사용자가 무엇을 입력해야 하는지와 입력 후 무엇이 달라지는지 연결한다.
- 첫 진입 화면에는 전체 기능 설명보다 시작 가능한 행동을 우선한다.

### 복잡한 정보를 나누는 기준

다음 조건 중 하나 이상이면 정보를 분리한다.

- 사용자가 한 번에 이해해야 할 판단 기준이 3개 이상이다.
- 입력 항목이 서로 다른 도메인에 속한다.
- 결과와 원인이 같은 화면에서 섞여 혼란을 만든다.
- 보조 정보가 핵심 CTA를 밀어낸다.
- 모바일에서 스크롤이 길어져 현재 위치를 잃기 쉽다.

### 메뉴와 페이지 확장 기준

- MVP의 단계형 흐름은 사용자가 순서대로 판단해야 하는 경우에 적합하다.
- 기능이 늘어날 때는 “입력”, “판독”, “가격”, “빌더”, “최종 출력”처럼 사용자 과업 기준으로 묶는다.
- 단순 기능 수 증가를 이유로 메뉴를 늘리지 않는다.
- 같은 데이터의 다른 관점이면 탭이나 필터를 검토하고, 다른 과업이면 별도 화면을 검토한다.

## 5. 화면 설계 원칙

### 각 화면의 기본 역할

모든 화면은 다음 중 하나의 주 역할을 가져야 한다.

| 화면 역할 | 예시 | 설계 기준 |
| --- | --- | --- |
| 시작 | 홈, 새 견적 시작 | 사용자가 즉시 시작하거나 복구할 수 있어야 함 |
| 입력 | 카드, 사양, 게임, 작업, 선호도 | 입력 목적과 저장 상태가 명확해야 함 |
| 판독 | 사양 결과 | 결과, 이유, 경고, 다음 행동이 함께 보여야 함 |
| 보강 | 가격 수집 | 부족한 데이터와 보강 방법을 구분해야 함 |
| 선택 | 단계별 빌더 | 후보 비교와 선택 결과가 연결되어야 함 |
| 출력 | 최종 견적 | 금액, 조건, 주의사항, 내보내기가 명확해야 함 |

### 화면 목적 명확성 기준

- 화면마다 가장 중요한 사용자 행동을 하나로 정의한다.
- 보조 행동은 주요 행동과 시각적으로 경쟁하지 않게 한다.
- 화면 목적이 “입력”인지 “비교”인지 “확인”인지 섞이면 분리 또는 단계화를 검토한다.

### 주요 액션과 보조 액션 구분

- 주요 액션은 사용자를 다음 단계로 진행시키는 행동이다.
- 보조 액션은 저장, 초기화, 상세 보기, 원문 확인, 건너뛰기처럼 흐름을 보완하는 행동이다.
- 위험하거나 되돌리기 어려운 행동은 주요 CTA처럼 보이지 않게 하고 확인 단계를 둔다.
- “다음”, “저장”, “선택”처럼 동작이 다른 버튼을 같은 위계로 반복하지 않는다.

### 한 화면에 너무 많은 기능을 넣지 않는 기준

다음 경우에는 화면 분리, 접힘, 탭, 단계화를 검토한다.

- 사용자가 현재 화면의 완료 조건을 설명하기 어렵다.
- CTA가 여러 개 있고 우선순위가 불명확하다.
- 오류와 경고가 핵심 입력보다 더 많이 보인다.
- 한 화면에서 입력, 계산, 선택, 출력이 동시에 일어난다.

### 초기 MVP 화면과 확장 화면 구분

- MVP 화면은 핵심 플로우 완료를 우선한다.
- 확장 기능은 진입점이나 데이터 구조만 준비하고, UI는 사용자가 실제로 사용할 수 있는 수준일 때 노출한다.
- “추후 지원 예정” 요소는 사용자의 현재 과업을 방해하지 않는 범위에서만 사용한다.

## 6. 시각 디자인 원칙

### 색상 체계 기준

색상은 브랜드 장식보다 정보 의미를 우선한다.

- 기본 색상은 신뢰감, 가독성, 긴 입력 흐름의 피로도 감소를 기준으로 정한다.
- 강조 색상은 주요 CTA와 선택 상태에 제한적으로 사용한다.
- 경고, 오류, 성공, 정보 상태 색상은 의미가 겹치지 않게 정의한다.
- 가격 할인, 카드 혜택, 위험 경고를 모두 같은 색으로 처리하지 않는다.
- 색상만으로 상태를 전달하지 않고 텍스트, 아이콘, 배지, 설명을 함께 사용한다.

### 타이포그래피 기준

- 제목은 화면 목적과 정보 그룹의 위계를 드러내는 데 사용한다.
- 긴 설명문보다 짧은 문장과 구조화된 항목을 우선한다.
- 가격, 부품명, 경고, 신뢰도처럼 비교해야 하는 값은 스캔하기 쉬운 체계를 사용한다.
- 카드나 패널 안에서 과도하게 큰 제목을 사용하지 않는다.
- 숫자와 단위는 일관된 표기 규칙을 둔다.

### 여백과 정렬 기준

- 여백은 장식이 아니라 정보 그룹을 구분하기 위해 사용한다.
- 같은 종류의 입력과 결과는 정렬 기준을 통일한다.
- 긴 단계형 흐름에서는 시선 이동이 예측 가능해야 한다.
- 모바일에서는 좌우 여백보다 세로 흐름의 명확성을 우선한다.
- 고정 수치보다 컴포넌트 계층과 정보 밀도에 맞는 토큰 체계를 사용한다.

### 카드, 섹션, 구분선, 배경 기준

- 카드는 반복되는 후보, 저장된 견적, 요약 항목처럼 하나의 독립된 단위를 표현할 때 사용한다.
- 섹션은 서로 다른 과업이나 정보 그룹을 나눌 때 사용한다.
- 구분선은 여백만으로 구분이 어려울 때 보조적으로 사용한다.
- 배경 색상은 정보 구조를 돕는 경우에만 사용하고 장식용으로 남용하지 않는다.
- 카드 안에 또 다른 카드를 중첩해 정보 위계를 흐리지 않는다.

### 아이콘 사용 기준

- 아이콘은 상태, 도구, 방향, 경고를 빠르게 인식시키는 데 사용한다.
- 의미가 명확하지 않은 아이콘은 텍스트나 툴팁 없이 단독 사용하지 않는다.
- 같은 의미의 아이콘은 서비스 전체에서 일관되게 사용한다.
- 장식 목적의 아이콘 반복은 피한다.

### 브랜드 톤 미확정 시 임시 기준

브랜드가 확정되기 전에는 다음을 임시 기준으로 둔다.

- 판매성보다 상담성과 신뢰성을 우선한다.
- 과장된 문구, 강한 대비, 지나친 애니메이션을 피한다.
- 부품 견적 서비스답게 데이터와 판단 근거가 주인공이 되게 한다.
- 브랜드 확정 후에도 정보 의미 색상과 상태 색상은 쉽게 바꾸지 않도록 토큰화한다.

### 디자인 토큰과 스타일 변수 관리

- 색상, 글자 크기, 간격, 테두리, 그림자, 상태 색상은 Tailwind theme 또는 CSS 변수 수준에서 관리한다.
- 컴포넌트 내부에 임의 값을 반복하지 않는다.
- 토큰 이름은 색상명보다 역할 중심으로 정의한다.
- 새 토큰은 기존 토큰으로 표현하기 어려운 실제 UI 문제가 있을 때만 추가한다.

## 7. 컴포넌트 사용 원칙

### 공통 컴포넌트를 먼저 정의해야 하는 이유

이 프로젝트는 같은 정보가 여러 화면에서 반복된다. 가격, 신뢰도, 경고, 추천 이유, 후보 선택, 입력 검증이 화면마다 다르게 표현되면 사용자는 서비스의 판단 기준을 신뢰하기 어렵다.

공통 컴포넌트는 다음을 안정화한다.

- 버튼 위계
- 입력 상태
- 가격 표시
- 신뢰도 배지
- 경고 메시지
- 후보 카드
- 단계 진행 표시
- 최종 견적 항목

### 기본 컴포넌트 역할 기준

| 컴포넌트 | 역할 기준 |
| --- | --- |
| 버튼 | 명확한 명령 수행. 주요/보조/위험/텍스트 버튼 위계를 구분 |
| 입력창 | 사용자가 직접 값을 제공. 라벨, 도움말, 오류를 함께 고려 |
| 체크박스 | 여러 값을 동시에 선택할 수 있을 때 사용 |
| 라디오/세그먼트 | 상호 배타적 선택에 사용 |
| 카드 | 반복 후보나 저장 항목처럼 독립 단위에 사용 |
| 모달 | 현재 흐름 위에서 짧은 확인이나 보조 작업이 필요할 때만 사용 |
| 탭 | 같은 데이터의 관점 전환에 사용 |
| 테이블 | 많은 항목을 행/열로 비교해야 할 때 사용 |
| 배지 | 상태, 신뢰도, 분류처럼 짧은 메타 정보를 표시 |
| 알림 | 사용자가 알아야 할 결과, 경고, 실패, 성공을 전달 |

### shadcn/ui 사용 원칙

- shadcn/ui는 기본 접근성, 상태, 스타일 일관성을 확보하기 위한 출발점으로 사용한다.
- 프로젝트 의미에 맞는 래퍼 컴포넌트를 만들어 가격, 경고, 신뢰도 같은 도메인 표현을 통일한다.
- 기본 컴포넌트 스타일을 화면마다 직접 덮어쓰기보다 변형 규칙을 컴포넌트 레벨에서 관리한다.
- 새 라이브러리 도입은 shadcn/ui로 해결하기 어렵고, 접근성·유지보수·번들 크기 측면에서 이득이 명확할 때만 검토한다.

### 커스텀 컴포넌트를 만들어야 하는 경우

- 같은 UI 패턴이 여러 화면에서 반복된다.
- 가격/신뢰도/경고처럼 도메인 의미가 강하다.
- 상태 조합이 복잡해 화면마다 구현하면 오류 가능성이 높다.
- 접근성 처리를 한 곳에서 보장해야 한다.

### 커스텀 컴포넌트를 만들지 말아야 하는 경우

- 한 화면에서만 쓰이며 의미가 단순하다.
- 기존 shadcn/ui 조합으로 충분하다.
- 추상화 이름이 실제 도메인 의미를 설명하지 못한다.
- props가 과도하게 늘어나 사용법이 더 복잡해진다.

### 재사용성과 과도한 추상화의 균형

MVP에서는 “반복되는 의미”를 기준으로 재사용한다. 단순히 모양이 비슷하다는 이유만으로 추상화하지 않는다. 기능 확장이 예상되더라도 실제 변형 기준이 보이기 전까지는 얕은 래퍼와 명확한 도메인 컴포넌트를 우선한다.

## 8. 사용자 흐름 기준

### 첫 진입부터 핵심 행동 완료까지

사용자는 처음 진입했을 때 다음을 즉시 이해해야 한다.

- 새 견적을 시작할 수 있다.
- 이전 입력을 이어갈 수 있다.
- 가격 분석이나 사양 가져오기 같은 보조 진입점이 있다.
- 최종적으로 견적표를 얻는 서비스다.

단, 첫 화면에서 전체 기능을 모두 설명하려 하지 않는다. 핵심 행동을 시작시키고, 필요한 설명은 흐름 안에서 제공한다.

### 진입, 탐색, 입력, 확인, 완료, 재방문 기준

| 단계 | 고려할 점 |
| --- | --- |
| 진입 | 시작/복구/빠른 분석 행동을 명확히 구분 |
| 탐색 | 현재 단계와 남은 단계를 알 수 있게 함 |
| 입력 | 필수/선택, 저장 상태, 건너뛰기 가능 여부를 표시 |
| 확인 | 입력 결과가 추천에 어떻게 반영됐는지 보여줌 |
| 완료 | 복사/이미지 저장/주의사항 확인을 지원 |
| 재방문 | localStorage 복구와 새 견적 시작을 혼동하지 않게 함 |

### CTA 배치 판단 기준

- CTA는 사용자가 현재 단계의 판단을 마친 뒤 자연스럽게 도달하는 위치에 둔다.
- 긴 입력에서는 상단과 하단 중 사용자의 흐름을 끊지 않는 위치를 검토한다.
- 모바일에서는 주요 CTA가 스크롤 끝에 묻히지 않게 하되, 화면을 가리는 고정 요소는 신중히 사용한다.
- CTA 문구는 “다음”보다 가능하면 다음 결과를 예측할 수 있게 쓴다.

### 길을 잃지 않게 하는 기준

- 단계형 흐름에는 현재 위치와 이전/다음 이동 방법을 제공한다.
- 사용자가 건너뛴 입력이 추천 품질에 미치는 영향을 알려준다.
- 저장 상태와 복구 가능성을 명확히 한다.
- 오류가 발생해도 어느 단계에서 무엇을 고치면 되는지 연결한다.

### 클릭과 단계 수를 줄이는 기준

- 필수 판단이 아닌 정보는 접거나 나중에 보강할 수 있게 한다.
- 기본값은 안전하고 보수적인 방향으로 제안하되, 사용자에게 숨기지 않는다.
- 같은 입력을 여러 화면에서 반복하지 않는다.
- 파싱으로 채운 값은 사용자가 한 번에 검토하고 수정할 수 있게 한다.

## 9. 폼 UX 기준

### 입력 항목 구성 기준

- 입력 항목은 추천 결과에 영향을 주는 이유가 있어야 한다.
- 서로 다른 목적의 입력을 한 그룹에 섞지 않는다.
- 사용자가 모를 수 있는 값은 “모름” 또는 “나중에 입력” 경로를 제공한다.
- 선택 입력은 결과 품질에 미치는 영향을 설명한다.

### 필수값과 선택값 구분

- 필수값은 다음 단계 진행에 꼭 필요한 경우에만 지정한다.
- 선택값은 비워도 흐름이 진행되어야 한다.
- 비어 있는 선택값 때문에 추천 품질이 낮아지면 결과 화면에서 신뢰도나 경고로 알려준다.

### 라벨, 플레이스홀더, 도움말 기준

- 라벨은 입력 대상 자체를 설명한다.
- 플레이스홀더는 예시로만 사용하고 라벨을 대체하지 않는다.
- 도움말은 입력값이 추천에 어떻게 쓰이는지 설명할 때 사용한다.
- 긴 도움말은 기본 화면을 밀어내지 않도록 접힘 또는 보조 텍스트로 처리한다.

### 검증 메시지 기준

- 무엇이 문제인지와 어떻게 고칠 수 있는지를 함께 말한다.
- 사용자를 탓하는 표현을 쓰지 않는다.
- 숫자, 단위, 형식 오류는 허용 가능한 예시를 제공한다.
- 파싱 실패는 오류가 아니라 보정이 필요한 상태로 표현한다.

### 제출 전/중/후 상태

| 상태 | 기준 |
| --- | --- |
| 제출 전 | 입력 누락, 선택값, 저장 여부를 확인 가능해야 함 |
| 제출 중 | 중복 제출을 막고 진행 중임을 표시 |
| 제출 후 성공 | 다음 단계 또는 결과 확인 행동을 제공 |
| 제출 후 실패 | 보존된 입력, 실패 이유, 재시도/수동 입력 경로를 제공 |

### 긴 폼을 나누는 기준

- 입력 주제가 달라지면 화면 또는 섹션을 나눈다.
- 사용자가 현재 단계의 완료 조건을 알 수 있어야 한다.
- 진행률은 심리적 부담을 줄이는 방향으로 사용하고, 정확한 수치가 부담을 키우면 단계명 중심으로 표현한다.

### 실수 복구 기준

- 사용자가 이전 단계로 돌아가도 입력이 유지되어야 한다.
- 자동 파싱 결과는 원문과 정규화 값을 구분해 수정 가능하게 한다.
- 위험한 초기화는 확인을 요구한다.
- 호환성 오류는 해당 선택을 수정할 수 있는 위치로 연결한다.

## 10. 상태 설계 기준

| 상태 | 왜 필요한가 | 설계 수준 |
| --- | --- | --- |
| 기본 상태 | 사용자가 정상적으로 읽고 행동하는 기준 상태 | 핵심 정보와 CTA가 명확해야 함 |
| 로딩 상태 | 파싱, 가격 조회, 추천 계산 중 불확실성을 줄임 | 무엇을 처리 중인지 표시하고 중복 행동을 방지 |
| 빈 데이터 상태 | 입력 전, 가격 없음, 후보 없음 상황을 정상 흐름으로 처리 | 이유와 다음 행동을 제공 |
| 오류 상태 | 실패를 복구 가능한 문제로 안내 | 실패 원인, 영향 범위, 재시도/대체 경로를 제공 |
| 성공 상태 | 사용자의 행동이 반영됐음을 확인 | 다음 단계 또는 결과 확인으로 연결 |
| 권한 없음 상태 | 향후 로그인/공유 확장 시 접근 제한을 설명 | 현재 MVP에서는 거의 사용하지 않되 확장 가능성 고려 |
| 비활성 상태 | 조건 미충족 또는 선택 불가를 표현 | 왜 비활성인지 설명 가능해야 함 |
| 제출 중 상태 | 중복 저장/조회/제출을 방지 | 입력 보존과 진행 표시가 필요 |

### 상태 표현 공통 기준

- 상태는 색상만으로 표현하지 않는다.
- 가격 조회 실패, 크롤러 실패, 데이터 부족은 전체 앱 오류로 처리하지 않는다.
- critical 호환성 오류와 단순 정보 부족 경고는 명확히 구분한다.
- 빈 상태는 단순히 “없음”이 아니라 다음 행동을 알려줘야 한다.

## 11. 데이터 표시 기준

### 목록, 카드, 표, 차트 선택 기준

| 표현 방식 | 적합한 경우 |
| --- | --- |
| 목록 | 순서와 상태를 빠르게 훑어야 할 때 |
| 카드 | 후보 하나가 여러 속성과 액션을 가질 때 |
| 표 | 다수 항목을 같은 기준으로 정밀 비교할 때 |
| 차트 | 추세나 비율을 직관적으로 보여줄 때 |

MVP에서는 차트보다 명확한 숫자, 배지, 비교 기준, 이유 문장을 우선한다. 차트는 사용자가 실제로 판단을 더 빨리 할 수 있을 때만 도입한다.

### 데이터가 적을 때와 많을 때

- 데이터가 적으면 설명과 다음 행동을 함께 보여준다.
- 데이터가 많으면 검색, 필터, 정렬, 접힘을 검토한다.
- 후보가 3개를 넘는다고 모두 같은 위계로 노출하지 않는다.
- 사용자의 선택에 직접 필요한 후보와 참고 후보를 구분한다.

### 정렬, 필터, 검색 기준

- 검색은 사용자가 이미 이름을 알고 찾는 경우에 적합하다.
- 필터는 사용자가 조건으로 범위를 줄이는 경우에 적합하다.
- 정렬은 같은 후보군을 가격, 점수, 신뢰도 등 다른 기준으로 비교할 때 적합하다.
- 기본 정렬은 서비스의 추천 기준과 일치해야 하며, 사용자가 바꿀 수 있다면 현재 정렬 기준을 표시한다.

### 상태값과 등급값 표시 기준

- 신뢰도, 경고, 수집 출처, 갱신 시각은 추천 판단에 영향을 주므로 일관된 위치와 형식으로 표시한다.
- 등급값은 숫자만 보여주지 말고 의미를 해석할 수 있는 짧은 설명을 붙인다.
- 미출시/추정 게임 데이터는 일반 공식 데이터와 분리해 표시한다.

### 행동으로 이어지게 하는 기준

데이터 표시는 “정보 제공”에서 끝나지 않아야 한다. 사용자가 다음 행동을 선택할 수 있어야 한다.

- 가격 신뢰도가 낮으면 가격 보강으로 연결한다.
- 호환성 경고가 있으면 관련 부품 선택으로 연결한다.
- 과투자 가능성이 있으면 더 낮은 후보를 검토할 수 있게 한다.
- 조건부 카드 혜택이면 적용 조건 확인을 안내한다.

## 12. 반응형 기준

### 공통 확인 기준

- 모든 주요 입력이 모바일, 태블릿, 데스크톱에서 가능해야 한다.
- 화면 폭이 바뀌어도 정보 우선순위가 뒤집히지 않아야 한다.
- 버튼, 입력, 선택 컨트롤은 터치하기 충분한 크기와 간격을 가져야 한다.
- 긴 부품명과 가격, 경고 문구가 컨테이너를 깨지 않아야 한다.
- 고정 요소가 입력 필드, 오류 문구, CTA를 가리지 않아야 한다.

### 모바일 우선순위 조정 기준

- 모바일에서는 입력 완료와 결과 확인을 우선하고, 세부 비교는 접거나 단계화한다.
- 요약 정보는 필요할 때 펼칠 수 있게 하되, 핵심 CTA를 가리지 않게 한다.
- 후보 비교가 어려우면 카드형 또는 요약형 비교를 검토한다.
- 긴 설명보다 짧은 상태 문구와 상세 보기 구조를 사용한다.

### 테이블과 복잡한 화면 기준

- 모바일에서 표가 읽기 어렵다면 행 단위 카드, 핵심 열 우선 표시, 상세 펼침을 검토한다.
- 가로 스크롤은 정밀 비교가 꼭 필요한 경우에만 사용하고, 스크롤 가능성을 명확히 한다.
- 최종 견적은 모바일에서도 부품별 항목을 읽고 복사/저장할 수 있어야 한다.

### 스크롤과 고정 버튼 기준

- 고정 CTA는 긴 입력에서 도움이 될 수 있지만, 화면을 가리면 안 된다.
- 사용자가 현재 위치를 잃기 쉬운 긴 흐름에는 단계 표시나 요약을 제공한다.
- 모바일 키보드가 열린 상태에서도 제출 버튼과 오류 메시지가 접근 가능해야 한다.

## 13. 접근성 기준

### 키보드 사용

- 모든 버튼, 링크, 입력, 선택 컨트롤은 키보드로 접근 가능해야 한다.
- 단계형 흐름에서 탭 순서는 화면의 시각적 흐름과 일치해야 한다.
- 모달과 드롭다운은 열림/닫힘, 포커스 이동, Escape 동작을 처리해야 한다.

### 포커스 표시

- 포커스 상태는 눈에 띄어야 하며 hover 상태와 혼동되지 않아야 한다.
- 커스텀 컴포넌트도 기본 브라우저 포커스 접근성을 잃지 않아야 한다.
- 오류 발생 시 관련 입력 또는 오류 요약으로 포커스를 안내하는 방식을 검토한다.

### 색상 대비

- 본문, 버튼, 배지, 경고 텍스트는 충분한 대비를 가져야 한다.
- 비활성 상태도 읽을 수 있어야 하며, 너무 흐려져 의미를 잃으면 안 된다.
- 가격 할인이나 위험 경고는 색상뿐 아니라 텍스트로 의미를 전달한다.

### 라벨과 aria

- 모든 입력은 시각적 라벨과 프로그램상 라벨을 가져야 한다.
- 도움말과 오류 메시지는 관련 입력과 연결한다.
- 아이콘 버튼은 접근 가능한 이름을 제공한다.
- 동적으로 바뀌는 결과나 오류는 필요 시 보조 기술이 인지할 수 있게 한다.

### 이미지 대체 텍스트

- 설명 목적의 이미지는 의미 있는 대체 텍스트를 제공한다.
- 장식 이미지는 보조 기술에서 무시되게 한다.
- 최종 견적 이미지 저장 기능은 이미지 자체와 별개로 텍스트 복사 경로를 반드시 제공한다.

### 모달과 드롭다운

- 열렸을 때 포커스가 내부로 이동해야 한다.
- 닫으면 호출한 요소로 포커스가 돌아와야 한다.
- 배경 스크롤과 키보드 탐색이 사용자를 혼란스럽게 하지 않아야 한다.

### MVP 최소 접근성 기준

- 키보드로 주요 플로우 완료 가능
- 모든 입력에 라벨 제공
- 색상만으로 상태 전달 금지
- 포커스 표시 유지
- 모달/드롭다운 접근성 보장
- 오류 메시지와 입력 연결

## 14. 마이크로카피 기준

### 버튼 문구

- 동작을 명확히 쓴다.
- 가능하면 사용자가 얻는 결과를 예측할 수 있게 한다.
- “확인”처럼 모호한 문구는 맥락이 분명할 때만 사용한다.
- 위험 행동은 결과를 드러내는 문구를 사용한다.

### 오류 메시지

- 사용자를 탓하지 않는다.
- 원인과 해결 방법을 함께 제공한다.
- 시스템 실패와 사용자 입력 오류를 구분한다.
- 가격/크롤링 실패는 대체 경로를 함께 안내한다.

### 빈 데이터 문구

- 빈 상태의 이유를 설명한다.
- 다음 행동을 제안한다.
- 빈 상태를 서비스 실패처럼 보이게 하지 않는다.

### 안내 문구

- 기능 설명보다 사용자가 얻는 판단 이익을 중심으로 쓴다.
- 긴 설명은 단계별로 나누거나 상세 보기로 분리한다.
- 기술 용어는 필요한 경우에만 쓰고 짧게 풀어쓴다.

### 전문 용어 기준

- CPU, GPU, RAM처럼 일반화된 용어는 사용할 수 있다.
- VRAM, 칩셋, 전원부, TDP처럼 해석이 필요한 용어는 설명 또는 툴팁을 검토한다.
- 용어 설명이 화면을 방해하면 도움말, 접힘, 용어 사전 확장을 검토한다.

### 상담형 문장 원칙

좋은 방향:

- “현재 조건에서는 이 후보가 요구 성능을 충족합니다.”
- “카드 조건이 맞을 때만 혜택가가 적용됩니다.”
- “가격 데이터가 부족해 판단 신뢰도는 낮습니다.”
- “이 후보는 케이스 길이 조건 확인이 필요합니다.”

피해야 할 방향:

- “무조건 사세요.”
- “최강 가성비입니다.”
- “이걸 안 사면 손해입니다.”
- “입력을 잘못했습니다.”

## 15. 애니메이션과 인터랙션 기준

### 사용해도 되는 경우

- 상태 변화가 일어났음을 부드럽게 알려줄 때
- 접힘/펼침, 단계 이동, 로딩 상태처럼 맥락 이해를 돕는 경우
- hover, focus, active 상태처럼 상호작용 가능성을 알려주는 경우

### 사용하지 말아야 하는 경우

- 추천 결과나 가격 판단보다 장식 효과가 더 눈에 띄는 경우
- 긴 입력 흐름에서 사용자의 속도를 늦추는 경우
- 로딩을 실제보다 길게 느끼게 하는 경우
- 접근성 설정을 무시하거나 어지러움을 유발할 수 있는 경우

### hover, focus, transition, loading 기준

- hover는 클릭 가능성과 선택 가능성을 알려주는 데 사용한다.
- focus는 키보드 사용자를 위한 핵심 상태이므로 제거하지 않는다.
- transition은 짧고 예측 가능해야 한다.
- loading은 어떤 작업이 진행 중인지 알려야 하며, 가능하면 스켈레톤보다 실제 영역 맥락을 유지한다.

### 성능과 접근성 기준

- 애니메이션은 레이아웃 흔들림을 만들지 않아야 한다.
- 사용자 환경의 모션 감소 설정을 존중한다.
- 저사양 기기에서도 입력과 스크롤이 끊기지 않아야 한다.

## 16. 기술 스택 연계 기준

### 현재 스택 반영

이 프로젝트의 MVP 기준 스택은 다음과 같다.

- Next.js App Router
- TypeScript
- Tailwind CSS
- shadcn/ui
- Zustand
- localStorage
- Next.js Route Handler

### Next.js App Router 기준

- 페이지는 사용자 과업 단위로 분리한다.
- 서버 Route Handler는 가격 조회, 파싱, 크롤러 어댑터처럼 클라이언트와 분리해야 하는 작업에 사용한다.
- UI 상태와 서버 실패 상태가 섞이지 않게 경계를 둔다.

### React/TypeScript 기준

- 도메인 타입은 `docs/03-data-model.md`의 구조를 우선한다.
- 컴포넌트 props는 화면 표현보다 도메인 의미를 드러내야 한다.
- 가격, 경고, 신뢰도, 추천 이유는 타입으로 상태를 명확히 구분한다.

### Tailwind CSS 기준

- 임의 클래스 반복보다 토큰과 컴포넌트 변형을 우선한다.
- 색상과 간격은 역할 중심으로 관리한다.
- 화면마다 독립적으로 스타일을 덮어써 일관성이 깨지지 않게 한다.

### shadcn/ui 기준

- 접근성과 기본 상호작용이 필요한 컴포넌트는 shadcn/ui를 우선 검토한다.
- 프로젝트 도메인에 맞는 래퍼를 두어 같은 의미의 UI가 화면마다 다르게 구현되지 않게 한다.
- 무조건 모든 UI를 shadcn/ui로 해결해야 하는 것은 아니며, 단순한 레이아웃은 일반 HTML/CSS 조합으로 충분할 수 있다.

### Zustand/localStorage 기준

- 입력 중인 값은 사용자가 잃어버리지 않게 저장한다.
- 저장 상태와 복구 상태를 UX에 반영한다.
- 스키마 버전 변경 시 초기화 또는 마이그레이션 메시지를 고려한다.

### 새 라이브러리 도입 기준

새 라이브러리는 다음 기준을 통과할 때만 검토한다.

- MVP 핵심 기능 구현에 필요하다.
- 접근성 또는 안정성을 직접 개선한다.
- 기존 스택으로 구현할 때 복잡도가 과도하다.
- 번들 크기, 유지보수성, 라이선스가 수용 가능하다.
- 서버리스 배포 제약과 충돌하지 않는다.

### 상태 처리

- [ ] 기본, 로딩, 빈 데이터, 오류, 성공 상태가 준비되어 있다.
- [ ] 가격 조회 실패와 데이터 부족이 복구 가능한 상태로 표현된다.
- [ ] 비활성 상태의 이유를 사용자가 알 수 있다.

### 폼 사용성

- [ ] 필수값과 선택값이 구분된다.
- [ ] 입력 오류는 원인과 해결 방법을 알려준다.
- [ ] 긴 폼은 주제별로 나뉘어 있다.
- [ ] 이전 단계로 돌아가도 입력이 유지된다.

### 문구 품질

- [ ] 판매 유도형 과장 표현을 쓰지 않는다.
- [ ] 사용자를 탓하지 않는다.
- [ ] 전문 용어는 필요한 경우 설명을 제공한다.
- [ ] 기능 설명보다 사용자 판단에 도움이 되는 문구를 쓴다.

### 상업용 서비스 신뢰감

- [ ] 가격 조건, 갱신 시각, 신뢰도, 주의사항이 숨겨지지 않는다.
- [ ] 추천 결과에 이유가 있다.
- [ ] 추정 데이터와 공식 데이터를 구분한다.
- [ ] 크롤링/파싱 실패에도 서비스가 무너지지 않는다.

### MVP 범위 준수

- [ ] 로그인, 결제, 공유 링크, PDF, 커뮤니티 등 제외 범위를 임의로 추가하지 않았다.
- [ ] 확장 기능은 실제 사용 가능한 수준이 아니면 과도하게 노출하지 않았다.
- [ ] 디자인 시스템은 필요한 수준까지만 정의했다.

### 결정 요약 표

| 항목 | MVP 결정 | 구현 기준 |

| 브랜드 톤 | 상담형 전문 서비스 중심, 가격 비교 도구형 보조 | 신뢰성 있는 상담 톤을 기본으로 하고 가격 비교는 판단 근거로만 사용 |
| 핵심 CTA 문구 | 첫 CTA: `내 조건으로 견적 만들기` | 단계 진행은 다음 결과가 드러나는 문구 사용 |

| 카드 혜택 조건 | 상세 조건 펼침 | 짧은 주의문을 항상 보이고, 조건 상세는 펼침으로 제공 |
| 최종 견적 이미지 | 별도 출력용 레이아웃 | 화면 캡처가 아니라 공유/저장에 맞춘 읽기 쉬운 견적 이미지 사용 |
| 데이터 출처 | 상세 메타 정보 | 배지와 함께 출처, 갱신 시각, confidence, warning을 확인 가능하게 표시 |
| 업그레이드 모드 | 제한적 경고 제공 | 진입점과 재사용 입력은 제공하되 전체 추천처럼 보이게 만들지 않음 |

### 각 결정의 이유

#### 브랜드 톤

MVP 브랜드 톤은 `상담형 전문 서비스`를 기본으로 확정한다. 다만 가격과 카드 혜택을 다루므로 `가격 비교 도구형`의 명확한 숫자 표현을 보조적으로 사용한다.

커뮤니티 친화형을 중심에 두지 않는 이유는 추천 신뢰도와 가격 조건을 다루는 서비스에서 가벼운 말투가 오해를 만들 수 있기 때문이다. 문장은 보수적이고 단정하지 않게 쓰되, 사용자가 판단할 수 있는 근거는 명확하게 제공한다.

#### 핵심 CTA 문구

첫 화면의 핵심 CTA는 `내 조건으로 견적 만들기`로 확정한다.

`새 견적 시작`은 기능 중심이라 사용자가 얻는 결과가 약하고, `PC 견적 진단 시작`은 진단 서비스처럼 보일 수 있다. 이 서비스의 핵심은 사용자의 조건을 반영한 견적 빌드업이므로 `내 조건으로 견적 만들기`가 가장 적합하다.

주요 진행 버튼은 다음 기준으로 작성한다.

| 위치 | 권장 문구 |
| --- | --- |
| 첫 화면 주요 CTA | 내 조건으로 견적 만들기 |
| 저장된 견적이 있을 때 | 이전 견적 이어가기 |
| 카드 선택 후 | 현재 PC 사양 입력하기 |
| 사양 입력 후 | 게임과 사용 목적 선택하기 |
| 조건 입력 후 | 사양 판독 결과 보기 |
| 판독 결과 후 | 가격 데이터 보강하기 |
| 가격 보강 후 | 부품 후보 선택하기 |
| 부품 선택 후 | 최종 견적 확인하기 |
| 최종 화면 | 견적 텍스트 복사, 견적 이미지 저장 |

#### 첫 화면 구조

첫 화면은 앱 진입 화면으로 설계한다. 가장 먼저 보여줄 행동은 `내 조건으로 견적 만들기`다.

우선순위는 다음과 같이 확정한다.

1. `내 조건으로 견적 만들기`
2. `이전 견적 이어가기`
3. `현재 PC 사양 가져오기`
4. `다나와 가격 붙여넣기 분석`

`이전 견적 이어가기`는 localStorage에 저장된 견적이 있을 때만 강하게 보여준다. `현재 PC 사양 가져오기`와 `다나와 가격 붙여넣기 분석`은 핵심 플로우를 대체하는 독립 서비스처럼 보이지 않게 보조 진입점으로 둔다.

#### 우선 지원 디바이스

MVP는 `데스크톱 우선, 모바일 보조 지원`으로 확정한다.

PC 견적 비교, 부품 후보 선택, 가격 조건 확인은 데스크톱에서 더 적합하다. 다만 모바일에서도 주요 입력, 저장된 견적 확인, 최종 견적 확인, 텍스트 복사는 가능해야 한다.

모바일 보조 지원은 모바일을 방치한다는 뜻이 아니다. 정밀 비교와 다중 패널 경험은 데스크톱에 최적화하고, 모바일은 단일 흐름과 카드형 확인을 우선한다는 뜻이다.

#### 다크모드

MVP에서는 다크모드를 포함하지 않는다. 대신 색상 토큰은 추후 다크모드 확장이 가능하도록 역할 기반으로 준비한다.

다크모드를 MVP에 포함하지 않는 이유는 가격, 신뢰도, 경고, 카드 혜택 상태 색상을 양쪽 테마에서 모두 검증해야 해 초기 품질 비용이 커지기 때문이다.

#### 추천 점수 노출 방식

추천은 `점수와 이유 병행`으로 확정한다.

점수를 완전히 숨기면 후보 비교가 어려워지고, 상세 점수를 모두 노출하면 초보 사용자가 숫자만 보고 오해할 수 있다. MVP에서는 대표 점수와 추천 이유를 함께 제공하되, 화면 위계는 이유와 경고를 더 중요하게 둔다.

권장 표현:

- 추천 적합도: 86
- 이유: 현재 해상도와 주사율 기준으로 성능 여유가 적절합니다.
- 주의: 카드 혜택 조건 확인이 필요합니다.

#### 가격 데이터 표시 방식

가격 데이터는 `요약 우선 + 상세 펼침`으로 확정한다.

기본 화면에서는 사용자가 행동에 필요한 최저가, 내 카드 혜택가, 배송비 포함 여부, 갱신 시각, 신뢰도를 먼저 본다. 원문 가격, 파싱 경고, 쇼핑몰별 세부 조건은 상세 펼침으로 제공한다.

#### 카드 혜택 조건 설명 깊이

카드 혜택 조건은 `상세 조건 펼침`으로 확정한다.

MVP는 카드사명 기준 단순 계산만 지원하므로, 짧은 주의문만으로는 실제 결제 조건에 대한 오해가 생길 수 있다. 카드별 상세 페이지는 MVP 범위를 넘기므로 만들지 않는다.

기본 화면에는 다음 수준의 문구를 항상 표시한다.

- 카드 혜택가는 카드사명 기준 단순 반영 금액입니다.
- 전월 실적, 할인 한도, 쿠폰 중복, 청구할인 시점은 MVP에서 계산하지 않습니다.

#### 최종 견적 이미지 저장 디자인

최종 견적 이미지는 `별도 출력용 레이아웃`으로 확정한다.

화면 그대로 저장하면 진행 UI, 접힘 패널, 보조 버튼이 함께 들어가 공유 결과물의 신뢰감이 떨어진다. 텍스트 중심 이미지만 사용하면 가격, 카드 혜택, 경고, 신뢰도 위계를 표현하기 어렵다.

별도 출력용 레이아웃은 다음을 포함한다.

- 견적 제목과 생성 시각
- 부품별 선택 목록
- 일반가, 혜택가, 배송비, 절감액
- 적용 카드 요약
- 주요 경고와 가격 신뢰도
- MVP 계산 한계 주의문

#### 데이터 출처 노출 방식

데이터 출처는 `상세 메타 정보`로 확정한다.

배지 수준만으로는 가격과 추천의 신뢰도를 설명하기 부족하고, 별도 출처 페이지는 MVP 범위를 넘는다. 각 데이터 블록에서 출처, 갱신 시각, confidence, warning을 확인할 수 있게 한다.

#### 업그레이드 모드 UI 범위

업그레이드 모드는 `제한적 경고 제공`으로 확정한다.

MVP의 기본은 전체 새 PC 견적이다. 업그레이드 모드는 기존 부품 재사용 의사와 호환성 경고를 받는 수준으로 제공하되, 전체 새 PC 견적과 같은 완성도 높은 추천 모드처럼 보이게 만들지 않는다.

표현 기준:

- 진입점은 제공한다.
- 기존 SSD, 케이스, 파워 재사용 의사는 저장한다.
- 재사용 부품이 선택된 경우 호환성 경고를 표시한다.
- “업그레이드 전용 최적 견적”처럼 오해될 문구는 쓰지 않는다.

### MVP에서 하지 말아야 할 UI

- 랜딩페이지처럼 긴 소개 섹션, 과장 문구, 마케팅형 히어로를 앞세우지 않는다.
- 가격 혜택을 “최저가 확정”처럼 표현하지 않는다.
- 추천 점수만 크게 보여주고 이유와 경고를 숨기지 않는다.
- 업그레이드 모드를 전체 견적과 같은 완성도처럼 보이게 하지 않는다.
- 다크모드 토글을 만들고 실제 상태 색상 검증을 생략하지 않는다.
- 모바일에서 데스크톱 표를 그대로 축소해 읽기 어렵게 만들지 않는다.
- 카드 혜택 조건, 배송비, 갱신 시각, 신뢰도 정보를 접어둔 채 기본 화면에서 완전히 숨기지 않는다.
- shadcn/ui 기본 컴포넌트를 화면마다 임의 스타일로 덮어써 일관성을 깨지 않는다.

### 구현자에게 전달할 핵심 UI 규칙 10개

1. 첫 화면의 가장 강한 CTA는 `내 조건으로 견적 만들기` 하나로 둔다.
2. 저장된 견적이 있을 때만 `이전 견적 이어가기`를 첫 화면의 강한 보조 행동으로 보여준다.
3. 추천 후보에는 대표 점수, 추천 이유, 경고를 함께 표시하고 이유를 점수보다 읽기 쉽게 둔다.
4. 모든 가격에는 혜택가 적용 조건, 신뢰도, 갱신 시각을 함께 표시한다.
5. 가격 원문, 파싱 경고, 쇼핑몰별 세부 조건은 상세 펼침으로 제공한다.
6. 카드 혜택가는 단순 계산이라는 주의문을 항상 보여주고 상세 조건은 펼침으로 제공한다.
7. 모바일에서는 후보 비교와 최종 견적을 단일 컬럼 또는 항목별 카드형으로 전환한다.
8. 업그레이드 모드는 재사용 입력과 호환성 경고까지만 제공하고 전체 추천 모드처럼 표현하지 않는다.
9. 최종 견적 이미지는 화면 캡처가 아니라 별도 출력용 레이아웃으로 생성한다.
10. 색상 토큰은 역할 기반으로 설계하되 MVP에는 다크모드 UI를 노출하지 않는다.

### 계속 사용자 결정이 필요한 항목

아래 항목은 UI 구현을 시작할 수 있을 정도로 기본 방향은 정했지만, 실제 브랜드/운영 전략에 따라 나중에 조정될 수 있다.

| 항목 | 기본 결정 | 추후 결정이 필요한 이유 |
| --- | --- | --- |
| 브랜드 네이밍과 로고 | 미정 | 시각 톤과 첫 인상에 직접 영향 |
| 실제 컬러 팔레트 | 역할 기반 토큰만 준비 | 브랜드 확정 후 최종 색상 결정 필요 |
| 사용성 테스트 우선순위 | 입력 완료율, 추천 이해도, 가격 오해 방지 | 실제 MVP 테스트 대상에 따라 순서 조정 가능 |
| 모바일 투자 범위 | 모바일 보조 지원 | 실제 모바일 유입 비중에 따라 동등 지원으로 상향 가능 |

## 19. 향후 확장 고려사항

### 기능 증가 시 UI가 무너지지 않게 하는 기준

- 새 기능은 기존 플로우의 어느 과업에 속하는지 먼저 판단한다.
- 같은 화면에 기능을 추가하기 전에 사용자의 현재 결정이 더 쉬워지는지 검토한다.
- 확장 기능은 기본 흐름을 방해하지 않는 보조 진입점으로 시작한다.
- 가격 히스토리, 알림, 공유 링크, 로그인, DB 저장은 각각 별도 상태와 권한 UX가 필요하다.

### 컴포넌트 확장 기준

- 기존 컴포넌트의 의미를 벗어나는 변형은 새 컴포넌트로 분리한다.
- 단순 스타일 차이만으로 컴포넌트를 늘리지 않는다.
- 도메인 컴포넌트는 데이터 타입과 상태 정의를 함께 검토한다.
- 경고, 신뢰도, 가격 표시 컴포넌트는 확장 시에도 의미가 변하지 않게 한다.

### 페이지 추가 기준

페이지를 추가하기 전에 다음을 확인한다.

- 기존 페이지의 하위 섹션으로 충분한가
- 같은 사용자 과업인가, 다른 과업인가
- URL로 직접 접근할 필요가 있는가
- 저장/복구/뒤로가기 UX가 명확한가
- 모바일에서 단계 수가 과도하게 늘어나지 않는가

### 디자인 시스템 고도화 기준

MVP 이후 다음 조건이 생기면 디자인 시스템을 고도화한다.

- 같은 컴포넌트 변형이 여러 화면에서 반복된다.
- 상태 색상이나 배지 의미가 늘어난다.
- 운영자 화면, 공유 화면, 사용자 앱 화면처럼 제품 표면이 분리된다.
- 다크모드나 브랜드 리뉴얼이 필요하다.
- 외부 사용자 테스트에서 일관성 문제가 반복적으로 나온다.

### 사용성 테스트와 피드백 반영 기준

- 사용자가 어디에서 입력을 포기하는지 확인한다.
- 추천 이유를 이해하는지 확인한다.
- 가격 혜택 조건을 오해하지 않는지 확인한다.
- 모바일에서 최종 견적을 확인하고 공유할 수 있는지 확인한다.
- 피드백은 개인 취향보다 반복되는 실패 패턴을 우선 반영한다.

## 핵심 요약

- 이 프로젝트는 랜딩페이지보다 단계형 앱 UX가 핵심이다.
- UI는 판매 유도가 아니라 보수적 상담, 근거, 신뢰도 전달을 우선해야 한다.
- 가격과 추천은 항상 조건, 이유, 신뢰도, 경고와 함께 표현한다.
- MVP UI 방향은 상담형 전문 서비스 중심으로 확정한다.
- 첫 화면의 핵심 CTA는 `내 조건으로 견적 만들기`로 확정한다.
- 추천은 대표 점수와 이유를 병행하되, 경고와 설명을 숨기지 않는다.
- 가격 정보는 요약 우선으로 보여주고 원문과 세부 조건은 상세 펼침으로 제공한다.
- MVP에서는 로그인/결제/공유 링크 같은 확장 기능을 임의로 추가하지 않는다.
- 화면 설계는 특정 레이아웃 고정이 아니라 사용자 과업, 정보 우선순위, 상태 처리 기준으로 판단한다.
- shadcn/ui와 Tailwind는 일관성과 접근성을 위한 기반으로 사용하되, 도메인 의미는 별도 컴포넌트로 통일한다.
